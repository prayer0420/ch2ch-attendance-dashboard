VM 이관 런북 핵심 정리
========================

1. 이 런북이 말하고 싶은 핵심

이 문서는 단순히 서버 파일을 복사하는 설명서가 아니다.
현재 서버(source)를 새 환경(target)에서도 같은 업무가 되도록 재현하고,
문제가 생기면 원래 서버로 돌아갈 수 있게 만드는 안전한 이관 절차다.

가장 짧게 말하면 다음과 같다.

  VM은 컴퓨터 본체를 복사해서 준비한다.
  데이터는 DB·Redis·Solr·Elasticsearch의 성격에 맞는 방법으로 복원한다.
  target은 원본과 분리해서 시험한다.
  CMS와 시뮬레이터가 실제로 동작하는 것을 확인한다.
  마지막에만 사용자 요청을 target으로 조금씩 보낸다.
  문제가 생기면 source로 되돌린다.


2. 우리 환경에 대입한 큰그림

  원본 Host: tc-xen02
    ├─ 기존 VM 101: 192.168.1.101
    ├─ 기존 VM 102: 192.168.1.102
    └─ 기존 VM 103: 192.168.1.103

                 VM 복사 또는 서비스별 백업·복원
                               ↓

  목적지 Host: tc-xen01
    ├─ 기존 VM xen01.01: 192.168.1.81 / Qdrant 01
    ├─ 기존 VM xen01.02: 192.168.1.82 / Elasticsearch 9.1.1
    └─ 기존 VM xen01.03: 192.168.1.83 / PostgreSQL·Gitea

주의: tc-xen01은 VM 이름이 아니라 VM을 실행하는 큰 Xen 호스트다.
xen01.01~03은 그 안에 있는 VM이다.


3. 가장 먼저 결정해야 하는 것

tc-xen01에는 이미 서비스가 있으므로 아래 중 하나를 먼저 결정해야 한다.

  A. 기존 목적지 VM을 보존하고 새 복사 VM을 만든다.
  B. 기존 목적지 서비스에 source 데이터를 서비스별로 복원한다.
  C. 기존 목적지 VM을 백업한 뒤 교체한다.

아무 결정 없이 source VM 디스크를 기존 target VM에 덮어쓰면
기존 Qdrant·Elasticsearch·PostgreSQL·Gitea 데이터가 사라질 수 있다.
따라서 기본 안전안은 A 또는 B이며, C는 별도 승인이 필요하다.


4. 런북 전체 순서

  ① G0: 현재 상태 조사와 B0 백업
     - VM, OS, CPU, RAM, 디스크, IP, hostname 기록
     - 실행 프로세스와 LISTEN 포트 기록
     - 설정파일, JAR, 환경변수, DB·검색 데이터 위치 기록
     - 복원 연습용 B0 백업 생성

  ② M0: VM 미러 또는 복사본 준비
     - VM을 target에 복사하거나 export/import
     - target에 기존 VM이 있으면 덮어쓰기 전 보존 여부 확인
     - source와 target을 같은 IP로 동시에 켜지 않음

  ③ R0/T0: target 격리 부팅과 리허설
     - 임시 hostname과 임시 IP 사용
     - 운영 L4·VIP·DNS에 target을 등록하지 않음
     - Scheduler와 자동 writer가 실행되지 않게 함
     - OS, mount, /data, Java, JAR, 서비스 상태 확인

  ④ 서비스별 데이터 복원
     - MariaDB: 전체 삭제·전체 복원 금지. Scheduler 영향 범위만 승인 후 정합화
     - Redis: 기존 cluster 재결합을 우선 확인. 필요하면 빈 cluster를 만들고 cache 재생성
     - ZooKeeper/Solr: 새 ZK ensemble, configset, 모든 collection BACKUP/RESTORE
     - Elasticsearch: 빈 cluster를 만들고 Snapshot/Restore. data 폴더 직접 복사 금지
     - Qdrant: collection과 대표 vector 검색을 확인하고 snapshot/backup 방식으로 복원
     - PostgreSQL: pg_dump/pg_restore 또는 승인된 복제 사용
     - Gitea: DB·Git 저장소·설정·첨부파일·비밀키를 함께 복원

  ⑤ 애플리케이션 연결 시험
     - Master → Engine → Gateway → CMS 순서로 연결 확인
     - 각 프로그램의 DB·Redis·Solr·Elasticsearch 주소 확인
     - CMS 화면뿐 아니라 로그인·검색·봇 생성·학습·배포·질문까지 시험
     - 시뮬레이터로 실제 업무 흐름을 끝까지 실행

  ⑥ B1 최종 동기화와 Cut-over
     - source Scheduler와 writer 중지
     - 진행 중 job이 0건인지 확인
     - MariaDB·Solr·Elasticsearch의 최종 백업
     - target에 마지막 변경분 복원
     - 특정 테스트 IP 또는 제한된 L4 경로로 먼저 연결
     - 승인 후 전체 운영 요청을 target으로 전환

  ⑦ 안정화와 Rollback
     - 로그, 오류율, 응답시간, CPU·RAM·디스크 확인
     - 문제가 있으면 target 요청을 막고 source 경로로 복귀
     - target에서 쓰기가 발생했다면 데이터 충돌을 먼저 판단
     - 안정화가 끝날 때까지 source·백업·원본 데이터를 삭제하지 않음


5. 왜 서비스마다 방법이 다른가

VM 복사는 컴퓨터의 운영체제와 프로그램 파일을 가져오는 일이다.
하지만 DB와 검색 시스템은 실행 중인 상태와 내부 구조가 있어서
일반 파일처럼 복사하면 깨질 수 있다.

  - MariaDB는 업무 장부이므로 필요한 범위만 정합화한다.
  - Redis는 cache라면 다시 만들 수 있지만 세션·queue라면 함부로 삭제할 수 없다.
  - Solr는 collection과 ZooKeeper 설정이 함께 맞아야 한다.
  - Elasticsearch는 index·shard·cluster 상태 때문에 Snapshot/Restore를 사용한다.
  - PostgreSQL은 DB 백업·복원으로 옮긴다.
  - Gitea는 DB만이 아니라 Git 저장소와 설정도 함께 필요하다.


6. 런북의 단계별 산출물

  - VM 인벤토리: source와 target의 이름·주소·자원·서비스 표
  - 연결표: 서비스가 어느 IP:PORT로 연결되는지 기록
  - B0 백업: 리허설용 백업과 복원 결과
  - B1 백업: 운영 전환 직전 최종 백업
  - 검증표: 프로세스·포트·API·데이터·업무 결과
  - 전환 기록: 언제 어떤 경로를 target으로 바꿨는지
  - 롤백 기록: 문제가 났을 때 어떻게 source로 돌아갔는지


7. 이 런북을 읽을 때 주의할 점

원본 런북은 VMware와 Oracle Linux 9.6을 전제로 작성되어 있다.
현재 실제 작업은 Xen과 Rocky Linux 9.6 환경이므로 원본의 명령어를
그대로 실행하는 것이 아니라 원칙과 순서를 가져와 Xen에 맞게 적용해야 한다.

검은 명령어가 있다고 해서 바로 실행하는 것이 아니다.
먼저 source인지 target인지, 조회인지 변경인지, 실제 주소와 UUID가 맞는지,
승인받은 명령인지 확인해야 한다.


8. 팀장님께 반드시 확인할 질문

  1) source는 tc-xen02, target Host는 tc-xen01이 맞는가?
  2) tc-xen01의 xen01.01~03 VM은 현재 실제 사용 중인가?
  3) 기존 target VM을 보존해야 하는가, 교체해도 되는가?
  4) 새 테스트 VM을 만들 CPU·RAM·SR 여유가 있는가?
  5) 192.168.1.81~83은 운영 IP인가, 테스트 IP인가?
  6) 기존 Qdrant collection을 보존해야 하는가?
  7) Elasticsearch 9.1.1로 어떤 방식으로 source index를 복원할 것인가?
  8) PostgreSQL과 Gitea의 DB·저장소를 반드시 보존해야 하는가?
  9) 임시 IP와 격리된 네트워크를 받을 수 있는가?
 10) Scheduler는 어느 VM 한 대에서만 실행할 것인가?
 11) CMS·Master·Engine·Gateway의 최종 연결 주소는 무엇인가?
 12) 운영 전환과 롤백을 승인할 사람은 누구인가?


한 문장 요약
------------

이 런북은 “VM을 복사하고 끝내자”가 아니라,
“원본을 보존한 채 새 Xen 호스트에 환경을 준비하고, 서비스별 데이터와 연결을
검증한 다음, 실제 업무 테스트를 통과했을 때만 운영 트래픽을 천천히 전환하자”는
안전한 이관 계획이다.
