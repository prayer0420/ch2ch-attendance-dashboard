1. 목적·범위

🧒 아주 쉽게 설명하면: 1. 목적·범위

이 부분은 이사 계획의 지도입니다.

이 문서는 현재 서버에서 새 환경으로 옮길 때 어디까지 다루고 어디부터는 다른 담당자와 상의해야 하는지를 정합니다. ‘포함’은 이번 작업의 범위이고, ‘별도 협의’는 네트워크·VMware·운영 중단처럼 다른 담당자의 승인이 필요한 부분이며, ‘금지’는 실수하면 원본 데이터를 잃을 수 있어 절대 함부로 하지 않는 행동입니다.

여기서 가장 중요한 사실은 목표가 Oracle Linux 9.6이라는 점과, 원본 OS 종류는 추측하지 말고 실제 서버에서 다시 확인해야 한다는 점입니다. 즉, 이 문서는 ‘무조건 그대로 실행하는 요리법’이 아니라, 현장 확인 결과에 따라 다음 행동을 선택하는 안전한 작업지도입니다.

이 부분에서 확인할 것: 실제 결과물: 작업 범위표, 원본 OS 확인 결과, 담당자 승인.

이 지침서는 EL7 계열 또는 Rocky Linux 8로 추정되는 운영 또는 운영 유사 3대 VM을 VMware 방식으로 복제해 Oracle Linux 9.6에서 동일 애플리케이션을 검증하고 전환하는 절차를 정의한다. AS-IS OS는 아직 확인되지 않았으므로 정확한 배포판·release·kernel·architecture를 작업 전 채증하며, 실측값이 본 문서의 추정과 다르면 호환성 판정을 다시 수행한다.

포함

파일·JAR 이관, OS/JDK/라이브러리 검증, MariaDB 미러 기동과 Scheduler 영향 데이터 재적재, Redis 재클러스터링과 cache 재배포, Solr collection 필수 이관, Elasticsearch Snapshot/Restore와 ILM·SLM 검증, 기능·장애 시험.

별도 협의

VMware 미러 생성과 OL9.6 전환 자체, L4/VIP 전환, 운영 DB 이중화·복제 솔루션, 방화벽·보안 정책 승인, 최종 업무 중단 공지.

금지

소스·대상 동시 동일 IP 사용, 미러된 클러스터 데이터의 무검증 기동, 리허설 데이터를 운영 소스로 역병합, JAR 재빌드·개명, 소스 코드 임의 변경.

AS-IS OS 미확정 — “Rocky 7”로 단정 금지 Rocky Linux의 첫 정식 릴리스는 8.4이므로 공식적인 Rocky Linux 7은 없다. 현장에서 “7대”라고 부르는 서버는 CentOS/RHEL/Oracle Linux 등 EL7 계열일 수 있다. 작업 승인 전에 각 원본 VM에서 /etc/os-release, release package, kernel, architecture, 설치 RPM과 native library 의존성을 채증한다. 본 런북의 목표와 최종 합격 환경은 Oracle Linux 9.6이다.

2. 작업 원칙과 전환 모델

🧒 아주 쉽게 설명하면: 2. 작업 원칙과 전환 모델

이 부분은 이관의 기본 약속입니다.

VMware 미러는 컴퓨터 한 대를 통째로 복사해 옮기는 출발점입니다. 하지만 안에 있는 Redis·MariaDB·Solr·Elasticsearch 같은 데이터는 각각 성격이 다르기 때문에, ‘VM을 복사했으니 모든 데이터가 완벽하게 옮겨졌다’고 보면 안 됩니다.

그래서 이 런북은 큰 컴퓨터는 미러로 준비하고, 데이터는 제품이 제공하는 안전한 백업·복원 방법을 사용합니다. MariaDB는 업무 데이터라 조심하고, Redis는 다시 만들 수 있는 cache인지 확인하며, Solr와 Elasticsearch는 각각 BACKUP/RESTORE와 Snapshot/Restore를 사용합니다.

  1. 미러는 운반본이다. 미러 생성 시점이 노드별로 달라도 바이너리·설정 보존에는 쓸 수 있으나 분산 데이터의 하나의 논리 시점을 보장하지 않는다.
  2. MariaDB의 기준은 미러다. database 전체 dump/restore를 하지 않는다. Scheduler 전용 테이블은 source 최종 data-only INSERT SQL을 만들고 target의 해당 데이터만 비운 뒤 재적재한다. 공용 업무 테이블은 관련 PK만 교정한다.
  3. Redis는 cache다. 미러된 RDB/AOF는 그대로 사용할 수 있으나 별도 이관 원본으로 만들지 않는다. 기존 cluster가 정상 재결합하면 유지하고, 실패하면 빈 cluster를 다시 구성한 뒤 시스템 배포 기능으로 cache를 재생성한다.
  4. Solr collection 이관은 필수다. ZooKeeper와 Solr의 미러 data를 최종 복구 원본으로 쓰지 않고, configset·alias와 모든 collection을 서비스 API의 BACKUP/RESTORE로 옮긴다.
  5. Elasticsearch는 Snapshot/Restore한다. 미러 data directory는 증적·원복용으로 보관한 뒤 target working data를 비우고 새 cluster UUID로 구성한다. index는 snapshot으로 복원하고 ILM·SLM·template·pipeline은 export/import 후 별도 검증한다.
  6. B0와 B1의 목적이 다르다. B0는 리허설과 복구 가능성 확인용이다. B1은 Scheduler와 모든 writer를 멈춘 뒤 만드는 Solr/ES 최종 백업 및 MariaDB Scheduler 영향 데이터의 최종 INSERT SQL이다. Redis 데이터 백업은 B1 필수 산출물이 아니다.
  7. 삭제 대신 보관 후 초기화한다. target임을 세 번 확인한 뒤 기존 동적 디렉터리를 외부 또는 hold 영역으로 이동하고, 신규 빈 경로를 만든다.
절대 안전 규칙 MariaDB의 DROP DATABASE, DROP TABLE, schema 전체 import와 전체 table TRUNCATE는 금지한다. 승인된 Scheduler 전용 테이블의 DELETE FROM은 target rollback INSERT SQL과 staging 검증을 먼저 확보한 경우에만 허용한다. Redis FLUSHALL/CLUSTER RESET과 Solr/ZK/ES data 이동은 target 식별 파일·IP·hostname을 대조하고 책임자가 서명한 뒤에만 수행한다. source에는 파괴 명령을 실행하지 않는다.

3.1 현재 VM 배포 JAR 기준 checksum

🧒 아주 쉽게 설명하면: 3.1 현재 VM 배포 JAR 기준 checksum

checksum은 파일의 지문입니다.

JAR 파일을 복사할 때 파일 이름만 같다고 같은 파일이라는 뜻은 아닙니다. SHA-256 checksum은 파일 내용을 계산한 긴 문자열이라서, 복사 전후 값이 같으면 내용이 바뀌지 않았다고 판단하는 데 도움을 줍니다.

이 값은 ‘이 프로그램을 새로 빌드해서 교체한다’는 뜻이 아닙니다. 현재 VM에서 실제로 실행하던 JAR을 원본으로 삼아 그대로 보존하고, target에서도 같은 지문인지 확인한다는 뜻입니다.

이 부분에서 확인할 것: 성공 기준: source와 target의 파일명·크기·권한·SHA-256이 승인된 기준과 일치.

로컬 개발 PC의 target 산출물이 아니라 미러 직전 현재 VM에 배포된 파일을 원본으로 삼는다. 다음 값은 현행 참고값이며 작업 시 다시 계산한다.

4.1 작업 전 필수조건

🧒 아주 쉽게 설명하면: 4.1 작업 전 필수조건

이 목록은 출발 신호가 아니라 안전벨트입니다.

백업이 있고, target 저장공간이 충분하고, 테스트 IP가 있고, 롤백 담당자가 정해져 있어야 작업을 시작할 수 있다는 뜻입니다. 하나라도 빠지면 문제 발생 시 멈추거나 되돌릴 수 없습니다.

특히 ‘운영 IP와 다른 임시 IP’, ‘Scheduler를 한 대만 켤 방법’, ‘source와 target을 분리할 네트워크’가 중요합니다.

이 부분에서 확인할 것: GO 조건: 모든 체크박스 완료와 담당자 승인. NO-GO 조건: 한 항목이라도 미확정.
  • 소스와 대상이 동시에 같은 IP/hostname/VIP로 통신하지 않는 격리 설계가 승인됐다.
  • 미러 디스크와 독립된 백업 저장소가 있고 용량·권한·checksum 복사가 검증됐다.
  • Solr 세 노드에서 같은 경로로 보이는 공유 BACKUP 저장소가 준비됐다.
  • Elasticsearch 세 노드의 path.repo와 snapshot repository가 미리 준비되고 verify에 성공했다.
  • 운영의 master DB와 모든 tenant DB, 실제 engine, 전체 용량, 가장 큰 테이블, dump/restore 예상 시간이 조사됐다.
  • MariaDB binlog 보존기간이 리허설 기간보다 길다. 현재 테스트베드 관찰값 7일을 운영값으로 가정하지 않는다.
  • JDK/JRE 8 설치 매체와 Oracle Linux 9.6용 필수 native library 패키지가 내부 저장소에 준비됐다.
  • 비밀값은 vault 또는 권한 0600 option file로 제공하고 명령행·문서·로그에 기록하지 않는다.

5. G0 — 사전 채증과 B0 리허설 백업

🧒 아주 쉽게 설명하면: 5. G0 — 사전 채증과 B0 리허설 백업

G0는 출발 전에 사진을 찍고 연습용 백업을 만드는 단계입니다.

채증은 현재 상태를 증거로 남기는 일입니다. 어떤 서비스가 살아 있고, 어떤 데이터가 몇 건이며, 어느 파일을 실행하는지 기록합니다. B0는 운영 전환 직전의 최종 백업이 아니라, 먼저 target에서 복원 연습을 해 보기 위한 백업입니다.

이 단계에서 서버를 바꾸는 것이 아니라 현재 상태를 읽고 저장합니다. 나중에 target 결과와 비교할 수 있도록 명령어 결과, checksum, 서비스 상태, 데이터 목록을 파일로 남깁니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: 원본의 현재 상태, 백업 저장 위치, 생성 시각, checksum, 복원 방법입니다. 백업은 파일 한 개를 복사하는 행동이 아니라 실패했을 때 돌아갈 지점을 만드는 일입니다.

B0와 B1: B0는 리허설 전 복원 연습용이고, B1은 최종 전환 직전 writer와 Scheduler를 멈춘 뒤 마지막 변경분을 고정하는 용도입니다. 이름이 비슷해도 시점과 목적이 다릅니다.

  1. 백업 대상을 정합니다.
  2. 파일·시각·크기를 기록합니다.
  3. SHA-256으로 변조 여부를 봅니다.
  4. target에서 실제 복원합니다.
  5. 성공·실패와 승인을 남깁니다.

초보자 원칙: ‘백업 성공’ 메시지만 믿지 말고 목록·checksum·복원 결과까지 확인합니다.

이 부분에서 확인할 것: 다음 단계로 가는 조건: B0 백업이 실제로 복원 가능한지 확인하고, 원본 변경 없이 기록 완료.

B0는 target 복원 절차와 Oracle Linux 9.6 호환성을 시험하기 위한 기준본이다. MariaDB 전체 dump는 만들지 않으며 Scheduler 전용 데이터와 공용 상태 후보만 선택 추출한다. Solr collection backup과 Elasticsearch snapshot의 성공을 확인하지 못하면 미러 단계로 넘어가지 않는다.

5.1 공통 현황 채증

🧒 아주 쉽게 설명하면: 5.1 공통 현황 채증

각 서버의 건강검진표를 만드는 일입니다.

CPU·메모리·디스크·OS·프로세스·포트·로그·설정 주소를 조사합니다. 의사가 환자의 체온과 혈압을 먼저 재듯이, 이관 전에 서버의 현재 모습을 먼저 알아야 합니다.

명령어의 목적은 ‘무언가를 고치는 것’이 아니라 ‘현재 상태를 읽는 것’입니다. 결과를 서버별 파일로 저장하면 101·102·103을 헷갈리지 않고 target과 비교할 수 있습니다.

이 부분에서 확인할 것: 성공 기준: 세 VM의 hostname, IP, OS, 서비스, 포트, 디스크와 연결 대상이 표로 정리됨.
  • 각 VM의 hostname, IP, OS/kernel, CPU architecture, 시간대/NTP, filesystem/mount, free space.
  • admin의 numeric UID/GID, 디렉터리 ownership/mode, SELinux context, file capabilities.
  • Java 경로·버전, 환경변수, 모든 native executable의 version과 ldd 결과.
  • systemd unit 전체 내용·enable 상태·실행 계정, 애플리케이션 appctl.sh 및 실제 JAR 파일명.
  • /application, /mariadb, 업무 파일 디렉터리의 파일 목록·크기·SHA-256.
  • listen port, 방화벽, hosts/DNS, L4 health URL, 각 서비스 클러스터 토폴로지와 데이터 건수.
  • 설정 파일은 백업하되 DB 암호, Jasypt 키, API key 등은 증적본에서 마스킹.

5.2 MariaDB B0 선택 데이터 추출

🧒 아주 쉽게 설명하면: 5.2 MariaDB B0 선택 데이터 추출

MariaDB에서 필요한 일부 데이터의 연습용 복사본을 만드는 단계입니다.

MariaDB에는 실제 업무 데이터가 있을 수 있으므로 데이터베이스 전체를 무작정 비우거나 복원하지 않습니다. Scheduler가 만드는 통계·배치 기록처럼 다시 넣어야 하는 범위만 골라서 INSERT SQL로 준비합니다.

B0는 연습용입니다. source의 데이터가 언제 기준인지 기록하고, target에 적용하기 전에 행 수·기본키·checksum을 비교합니다. MyISAM 테이블은 일반적인 transaction 되돌리기가 제한될 수 있어 원복 SQL을 별도로 준비해야 합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source DB의 현재 데이터, target DB의 table 구조, Scheduler가 건드리는 table 목록, 그리고 승인된 적용 범위입니다. DB는 단순한 파일 창고가 아니라 여러 프로그램이 계속 읽고 쓰는 업무 장부이므로, ‘파일이 복사됐나’보다 ‘어떤 행이 같은가’를 확인합니다.

실제 흐름: 먼저 읽기 명령으로 접속·table·행 수·진행 중 작업을 확인합니다. 그다음 writer와 Scheduler를 멈추고 source에서 승인된 data-only INSERT SQL을 만듭니다. target에서는 승인된 범위만 preclear하고 INSERT한 뒤 source와 count·기본키·checksum을 비교합니다. 나머지 업무 원본 table은 건드리지 않는 것이 기본입니다.

  1. 읽기: DB가 살아 있고 구조가 맞는지 봅니다.
  2. 고정: 더 이상 행이 변하지 않도록 writer를 멈춥니다.
  3. 적용: A그룹 전량 또는 B그룹 후보 PK만 처리합니다.
  4. 비교: 다르면 성공으로 보지 않고 멈춥니다.

가장 중요한 이유: MyISAM에서는 실패하면 DB가 자동으로 원래 상태로 돌아온다고 가정하면 안 됩니다. 따라서 지우기 전에 before-image와 원복 INSERT SQL을 먼저 준비합니다.

이 부분에서 확인할 것: 금지: source에서 DROP/TRUNCATE, 승인 없는 전체 DB dump/restore.
MyISAM 주의 현재 테스트베드는 모든 업무 테이블이 MyISAM이다. --single-transaction은 일관성을 보장하지 않는다. 선택 데이터 추출 중에도 Scheduler와 관련 writer를 멈추고 --lock-all-tables로 일관된 시점을 잡는다. database 전체 dump·restore는 본 절차의 대상이 아니다.
모든 활성 tenant schema 조사 코드는 master DB의 tbl_manage_tenant.manage_schema_id → tbl_manage_schema 관계에서 tenant별 접속정보를 읽어 DataSource를 동적으로 만든다. 아래 Scheduler 전용 통계 테이블은 각 활성 tenant DB에 있을 수 있으므로 master DB 한 곳만 보고 끝내지 않는다. 서로 다른 DB 서버라면 각 서버의 writer를 멈춘 시각과 추출 완료시각을 기록한다. 
SELECT mt.code, mt.name, ms.prefix_url, ms.schema_name, ms.user_name
FROM tbl_manage_tenant mt
JOIN tbl_manage_schema ms ON ms.id = mt.manage_schema_id
WHERE COALESCE(mt.is_del, 'N') = 'N';
  1. Scheduler를 먼저 중지하고 신규 배포·학습·통계 job이 시작되지 않음을 확인한다.
  2. 공용 예약 배포 상태까지 추출할 때는 CMS/Master 등 관련 writer도 잠시 차단한다.
  3. 암호는 권한 0600인 <SOURCE_DB_OPTION_FILE>에서 읽는다.
  4. master DB에서는 tbl_batch_log, 각 tenant DB에서는 9개 통계 table만 data-only·명시 컬럼 INSERT 형식으로 추출한다. 테스트베드처럼 master/tenant가 같은 schema일 때만 10개를 한 파일로 합친다. DDL, 사용자, GRANT, system DB는 포함하지 않는다.
mariadb-dump \
  --defaults-extra-file=<SOURCE_DB_OPTION_FILE> \
  --host="${SRC_DB_HOST}" --port="${SRC_DB_PORT}" \
  --no-create-info --complete-insert --skip-extended-insert \
  --skip-triggers --quick --lock-all-tables --hex-blob \

5.3 Redis B0 상태 채증

🧒 아주 쉽게 설명하면: 5.3 Redis B0 상태 채증

Redis cluster의 자리 배치표를 만드는 단계입니다.

Redis는 여러 대가 master와 replica로 나뉘고, 16,384개의 slot에 데이터를 나누어 맡길 수 있습니다. 따라서 ‘Redis 프로세스가 켜져 있다’보다 어느 노드가 어떤 역할인지와 모든 slot이 정상인지가 중요합니다.

RDB·AOF·cluster state 파일은 바로 새 cluster에 덮어쓰지 않고 hold 영역에 보관합니다. target에서 기존 cluster를 재결합할지, 빈 cluster를 만들고 cache를 다시 생성할지 결정할 수 있도록 상태를 기록합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Redis 노드의 주소·port·master/replica 역할·node ID·slot 상태와 AOF/RDB 파일 정보입니다. Redis가 cache만 저장하는지, 로그인 세션·queue·업무 상태도 저장하는지는 애플리케이션 설정으로 확인합니다.

실제 흐름: PONG은 한 노드가 대답했다는 뜻이고, cluster_state:ok와 모든 slot 정상은 집단 전체가 일할 준비가 됐다는 뜻입니다. 기존 cluster 재결합이 안전하면 유지하고, 주소·node ID·slot이 꼬이면 빈 3 master/3 replica를 구성한 뒤 cache를 다시 만듭니다.

  1. 노드와 역할을 기록합니다.
  2. source와 target이 동시에 같은 cluster가 되지 않게 합니다.
  3. 재결합 또는 새 cluster 중 하나를 선택합니다.
  4. cache 재생성 뒤 TTL·대표 기능을 확인합니다.

주의: ‘Redis니까 지워도 된다’가 아닙니다. cache라면 다시 만들 수 있지만 세션·queue라면 초기화가 곧 업무 영향일 수 있으므로 담당자 승인이 필요합니다.

이 부분에서 확인할 것: 성공 기준: master/replica·slot·node ID·AOF/RDB 경로와 checksum 기록.
  1. 7000이 master라고 가정하지 말고 CLUSTER NODES와 각 노드의 INFO replication으로 현재 master 세 개를 식별한다.
  2. 모든 7000/7001의 host:port, node ID, master/replica 관계, slot, DBSIZE, INFO keyspace, dir, RDB/AOF와 자동 cluster state 파일 경로·checksum을 기록한다.
  3. RDB/AOF는 VMware 미러본과 함께 비상 원복본으로 보관할 수 있으나 Redis 데이터의 별도 B0/B1 이관 산출물로 요구하지 않는다.
/application/redis/bin/redis-cli -h "${REDIS_HOST}" -p "${REDIS_PORT}" CLUSTER NODES
/application/redis/bin/redis-cli -h "${REDIS_HOST}" -p "${REDIS_PORT}" CLUSTER INFO
/application/redis/bin/redis-cli -h "${REDIS_HOST}" -p "${REDIS_PORT}" INFO persistence
/application/redis/bin/redis-cli -h "${REDIS_HOST}" -p "${REDIS_PORT}" INFO replication

AOF가 활성화된 인스턴스는 시작할 때 RDB보다 AOF를 우선 사용할 수 있으므로 RDB만 교체하거나 삭제하지 않는다. 검사 도구의 --fix는 원본에 실행하지 않는다.

5.4 Solr/ZooKeeper B0 백업

🧒 아주 쉽게 설명하면: 5.4 Solr/ZooKeeper B0 백업

검색 설계도와 검색 문서를 연습용으로 보관하는 단계입니다.

ZooKeeper는 SolrCloud가 어느 서버와 collection을 사용할지 조정하는 역할이고, Solr collection은 실제 검색 문서 묶음입니다. 둘 중 하나만 옮기면 화면은 떠도 검색이 실패할 수 있습니다.

configset은 검색 규칙과 필드 설계도이고, collection backup은 실제 문서입니다. 모든 collection과 alias를 목록으로 만든 뒤 collection별 BACKUP이 완료됐는지 확인합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: ZooKeeper ensemble 주소와 myid, Solr node 주소, configset, collection 목록, shard·replica·leader·alias 정보입니다. ZooKeeper는 SolrCloud의 조정자이고 Solr는 실제 검색 문서를 제공하므로 둘을 한 세트로 봅니다.

실제 흐름: 새 ZooKeeper가 quorum을 만든 뒤 검색 규칙인 configset을 올립니다. 그다음 source의 모든 collection을 하나씩 BACKUP/RESTORE합니다. 복원 후에는 이름만 보지 않고 leader·replica·alias·문서 수·대표 한국어 검색을 확인합니다.

  1. 새 ZK ensemble을 준비합니다.
  2. Solr가 새 ZK를 보게 합니다.
  3. configset과 collection을 복원합니다.
  4. shard·replica·leader·alias·검색을 검사합니다.

자주 하는 착각: Solr 8983 port가 열려 있어도 collection이나 leader가 없으면 검색 시스템은 완성되지 않은 것입니다. ZK의 ruok 응답도 프로세스 생존 확인일 뿐 quorum 전체 정상 판정은 아닙니다.

이 부분에서 확인할 것: 성공 기준: source collection 목록과 backup 완료 목록이 하나도 빠짐없이 일치.
  1. CLUSTERSTATUS, live node, collection/shard/replica/leader/configName, alias, collection별 numFound, configset, ktnori JAR 위치/checksum을 저장한다.
  2. 각 collection에 hard commit을 실행한다. soft commit으로만 보이는 문서는 BACKUP에 포함되지 않을 수 있다.
  3. 세 Solr 노드에 같은 경로로 mount된 저장소에 collection별 BACKUP을 비동기로 실행하고 REQUESTSTATUS=completed를 확인한다.
  4. chat-base-config를 solr zk downconfig로 별도 저장하고, 존재하는 security.json, clusterprops.json, aliases.json, roles.json을 별도 export한다.
curl -fsS -X POST \
  "${SRC_SOLR_URL}/solr/${COLLECTION}/update?waitSearcher=true" \
  -H "Content-Type: application/json" --data-binary '{"commit":{}}'

curl -fsSG "${SRC_SOLR_URL}/solr/admin/collections" \
  --data-urlencode "action=BACKUP" \
  --data-urlencode "collection=${COLLECTION}" \
  --data-urlencode "name=${BACKUP_NAME}" \
  --data-urlencode "location=${SOLR_BACKUP_LOCATION}" \
  --data-urlencode "async=${REQUEST_ID}" --data-urlencode "wt=json"

기존 ZooKeeper의 version-2는 장애 분석용으로만 보관한다. 신규 ensemble에 복원하지 않는다. 특히 TC_CALLBOT_A BACKUP 성공과 checksum이 없으면 G0 실패다.

5.5 Elasticsearch B0 snapshot

🧒 아주 쉽게 설명하면: 5.5 Elasticsearch B0 snapshot

Elasticsearch의 검색 데이터를 공식 백업 방식으로 찍는 단계입니다.

Snapshot은 Elasticsearch가 자신의 index와 shard 구조를 이해한 상태로 저장하는 백업입니다. 실행 중인 data 폴더를 파일 복사하는 것보다 cluster가 읽을 수 있는 형식으로 복원하기 쉽습니다.

repository는 Snapshot을 넣어 둘 공용 창고이고, B0 snapshot은 target에서 복원 연습을 위한 백업입니다. index뿐 아니라 template·pipeline·ILM·SLM 정책을 별도로 확인해야 합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Elasticsearch node·cluster 정보, index·shard·alias 목록, Snapshot repository, template·pipeline·ILM·SLM 정책입니다. Elasticsearch는 index를 여러 shard로 나누어 저장하므로 data 폴더를 일반 파일처럼 복사하지 않습니다.

실제 흐름: target에서 새 빈 cluster를 준비하고 repository를 등록한 뒤 성공한 Snapshot을 restore합니다. 복원 후 cluster health·node·index·shard를 보고, 정책 객체는 별도로 비교합니다. green은 shard 배치가 정상이라는 뜻이지 업무 검색까지 자동 보장한다는 뜻은 아닙니다.

  1. 새 cluster와 repository를 준비합니다.
  2. 필요한 snapshot과 index를 복원합니다.
  3. template·pipeline·ILM·SLM을 따로 확인합니다.
  4. 대표 검색·정렬·aggregation·재기동을 시험합니다.

raw data 폴더를 피하는 이유: 그 안에는 cluster UUID와 shard 상태 같은 내부 정보가 들어 있어 버전·노드·시점이 맞지 않으면 cluster가 깨질 수 있습니다.

이 부분에서 확인할 것: 성공 기준: snapshot SUCCESS, 실패 shard 0, 예상 index와 정책 목록 기록.

현재 테스트베드에는 snapshot repository가 없는 것으로 확인됐다. 미러 전 세 노드에 공유 repository와 path.repo를 준비하고 _verify에 성공해야 한다. 이 정적 설정에 rolling restart가 필요하면 별도 사전 작업으로 승인받는다.

6. M0 — VMware 미러 생성·인수

🧒 아주 쉽게 설명하면: 6. M0 — VMware 미러 생성·인수

VM 한 대를 통째로 복사해 새 장소에 가져오는 단계입니다.

VM은 가상 컴퓨터입니다. VMware 미러에는 보통 가상 디스크 안의 OS와 설치된 프로그램, 설정 파일이 함께 들어갑니다. 그래서 OS를 새로 설치하는 것보다 현재 상태를 빠르게 재현할 수 있습니다.

하지만 미러는 ‘안전하게 운영할 준비가 끝났다’는 뜻이 아닙니다. 복사본은 원본과 같은 IP·hostname·cluster 정보를 가질 수 있으므로, target에서는 반드시 격리된 상태로 첫 부팅을 합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source VM의 CPU·RAM·디스크·NIC·OS·서비스와 target host의 저장공간·네트워크·자원입니다. VM은 가상 CPU·메모리·디스크·네트워크 카드를 가진 컴퓨터입니다.

실제 흐름: 가상화 담당자가 VM을 복사하거나 export/import합니다. 복사본을 처음 켤 때는 원본과 다른 임시 IP·hostname을 사용합니다. 부팅 후 OS·mount·/data·자동기동 서비스·Scheduler 상태를 확인합니다.

  1. source 상태와 백업을 고정합니다.
  2. target 저장소와 network를 확인합니다.
  3. VM을 복사·인수합니다.
  4. 임시 주소로 격리 부팅합니다.
  5. 원본과 충돌이 없는지 확인합니다.

비유: VM 복사는 집 전체를 새 동네에 복사하는 일입니다. 주소판과 전화번호가 예전 집과 같으면 우편과 전화가 섞이므로, 새 주소를 붙이고 손님을 받기 전까지 격리합니다.

이 부분에서 확인할 것: 인수 기준: VM 이름·UUID·디스크·NIC·전원 상태 확인, 원본 보존.

들어오는 자료: source VM의 CPU·RAM·디스크·NIC·OS·서비스와 target host의 저장공간·네트워크·자원입니다. VM은 가상 CPU·메모리·디스크·네트워크 카드를 가진 컴퓨터입니다.

  1. source 상태와 백업을 고정합니다.
  2. target 저장소와 network를 확인합니다.
  3. VM을 복사·인수합니다.
  4. 임시 주소로 격리 부팅합니다.
  5. 원본과 충돌이 없는지 확인합니다.

비유: VM 복사는 집 전체를 새 동네에 복사하는 일입니다. 주소판과 전화번호가 예전 집과 같으면 우편과 전화가 섞이므로, 새 주소를 붙이고 손님을 받기 전까지 격리합니다.

이 부분에서 확인할 것: 확인할 것: target host, datastore/SR, network, VM 중지 시간, snapshot 보존 기간.
  • 가능하면 3 VM을 같은 consistency group으로 처리하고 VMware Tools guest quiescing을 사용한다.
  • 메모리 상태를 복제하지 않는다. 대상은 전원이 꺼진 상태, NIC disconnected 또는 격리 포트그룹으로 인계한다.
  • 독립 디스크/RDM/외부 mount가 미러 범위에서 빠지는지 사전에 명시한다.
  • VM별 snapshot/clone ID, 복제 시작·종료 시각, quiesce 성공 여부를 인계서에 남긴다.
  • source VM은 최종 cutover/rollback 종료 전 삭제·업그레이드·재구성하지 않는다.
Hot mirror의 한계 사용량이 0인 시점이라도 DB buffer, AOF, Lucene segment, ZooKeeper epoch와 세 VM의 복제 시점은 다를 수 있다. 사용량 0은 위험을 낮출 뿐 서비스 단위 snapshot을 대체하지 않는다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source VM의 CPU·RAM·디스크·NIC·OS·서비스와 target host의 저장공간·네트워크·자원입니다. VM은 가상 CPU·메모리·디스크·네트워크 카드를 가진 컴퓨터입니다.

  1. source 상태와 백업을 고정합니다.
  2. target 저장소와 network를 확인합니다.
  3. VM을 복사·인수합니다.
  4. 임시 주소로 격리 부팅합니다.
  5. 원본과 충돌이 없는지 확인합니다.

비유: VM 복사는 집 전체를 새 동네에 복사하는 일입니다. 주소판과 전화번호가 예전 집과 같으면 우편과 전화가 섞이므로, 새 주소를 붙이고 손님을 받기 전까지 격리합니다.

이 부분에서 확인할 것: 절대 하지 않기: 원본과 target의 동일 IP 동시 기동, target의 즉시 L4 등록.
  1. 운영망과 분리된 포트그룹에서 한 대씩 부팅한다. source와 동일 IP가 라우팅되지 않아야 한다.
  2. 모든 애플리케이션, Scheduler, MariaDB, Redis, ZooKeeper, Solr, Elasticsearch, Kibana의 자동기동을 차단한 상태인지 확인한다.
  3. 대상 식별 파일을 각 VM에 만들고 변경 작업 전 항상 파일 내용·hostname·target IP를 대조한다.
  4. 미러 직후의 /application, /mariadb, /logs는 원본 상태 보관본으로 snapshot/hold 처리한다.
  5. 새 IP/hostname/hosts/DNS를 적용하되 L4 pool에는 아직 넣지 않는다.

7.2 호스트 호환성

🧒 아주 쉽게 설명하면: 7.2 호스트 호환성

기존 프로그램이 새 OS에서 달릴 수 있는지 시험하는 단계입니다.

JAR 파일은 Java가 필요하고, Python 프로그램은 Python과 모듈이 필요하며, native library는 OS의 라이브러리와 CPU 환경의 영향을 받을 수 있습니다. 파일이 있다고 실행되는 것은 아닙니다.

같은 파일을 target에 놓은 뒤 ‘실행 가능 여부’, ‘로그 오류’, ‘필요한 포트’, ‘설정파일 경로’를 확인합니다. 오류가 나면 소스 코드를 바꾸기보다 먼저 Java 버전·권한·환경변수·라이브러리를 비교합니다.

이 부분에서 확인할 것: 성공 기준: 승인된 JDK/라이브러리에서 실제 JAR과 미들웨어가 오류 없이 기동.
  • Oracle Linux 9.6 release/kernel/architecture, CPU flags, locale, KST/NTP, hostname/IP가 설계와 일치한다.
  • admin 계정의 UID/GID를 확인하고 /application, /mariadb, /logs를 admin:admin으로 정리한다.
  • OpenJDK/JRE 8을 승인된 배포판으로 설치하고 실제 모든 JAR에 대해 java -version과 기동 시험을 한다.
  • Redis/MariaDB 등 native binary마다 동적 라이브러리 누락, OpenSSL ABI, glibc, libaio, zlib을 검사한다.
  • SELinux enforcing 상태에서 서비스별 쓰기 디렉터리와 포트를 허용한다. 문제 해결을 위해 SELinux를 영구 비활성화하지 않는다.
  • systemd unit의 경로, LimitNOFILE/NPROC, vm.max_map_count, transparent huge page, ulimit 값을 source manifest와 대조한다.
  • firewall에는 7000/7001과 cluster bus 17000/17001, ZK 2181/2888/3888, Solr 8983, ES 9200/9300 및 앱 포트를 승인된 내부 대역에만 개방한다.

JAR·스크립트·설정파일·업로드 파일·systemd unit을 복사하고 checksum과 소유자를 확인합니다. 데이터베이스나 Elasticsearch data 폴더까지 같은 방식으로 덮어쓰라는 뜻은 아닙니다.

8. MariaDB 미러 기동·Scheduler 데이터 재적재

🧒 아주 쉽게 설명하면: 8. MariaDB 미러 기동·Scheduler 데이터 재적재

MariaDB를 원본 미러 기준으로 살리고, Scheduler가 바꾸는 일부 데이터만 정리하는 단계입니다.

MariaDB는 업무의 오래 보존해야 하는 정보가 있을 수 있어 전체를 새로 만들지 않습니다. 미러 DB를 기준으로 유지하고, Scheduler가 생성하거나 변경하는 범위만 source의 최종 INSERT SQL로 target에 맞춥니다.

중요한 순서는 writer와 Scheduler를 멈추고, 데이터가 더 이상 변하지 않는지 확인한 뒤, 승인된 범위만 처리하는 것입니다. target에서 실행하더라도 대상 DB인지 세 번 확인합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source DB의 현재 데이터, target DB의 table 구조, Scheduler가 건드리는 table 목록, 그리고 승인된 적용 범위입니다. DB는 단순한 파일 창고가 아니라 여러 프로그램이 계속 읽고 쓰는 업무 장부이므로, ‘파일이 복사됐나’보다 ‘어떤 행이 같은가’를 확인합니다.

실제 흐름: 먼저 읽기 명령으로 접속·table·행 수·진행 중 작업을 확인합니다. 그다음 writer와 Scheduler를 멈추고 source에서 승인된 data-only INSERT SQL을 만듭니다. target에서는 승인된 범위만 preclear하고 INSERT한 뒤 source와 count·기본키·checksum을 비교합니다. 나머지 업무 원본 table은 건드리지 않는 것이 기본입니다.

  1. 읽기: DB가 살아 있고 구조가 맞는지 봅니다.
  2. 고정: 더 이상 행이 변하지 않도록 writer를 멈춥니다.
  3. 적용: A그룹 전량 또는 B그룹 후보 PK만 처리합니다.
  4. 비교: 다르면 성공으로 보지 않고 멈춥니다.

가장 중요한 이유: MyISAM에서는 실패하면 DB가 자동으로 원래 상태로 돌아온다고 가정하면 안 됩니다. 따라서 지우기 전에 before-image와 원복 INSERT SQL을 먼저 준비합니다.

이 부분에서 확인할 것: 금지: 운영 source에서 전체 삭제, target의 모든 table 무차별 초기화.
DB 처리 원칙 미러된 /mariadb/data와 database/schema/table은 그대로 유지한다. 전체 DB dump·전체 restore·schema 재생성은 하지 않는다. Scheduler가 독점 생성하는 데이터만 source 최종 INSERT SQL로 전량 교체하고, 업무 애플리케이션과 함께 쓰는 상태는 Scheduler 영향 PK만 교정한다.

  3. 운영망·원본 DB와 격리한 상태로 미러 DB를 기동한다. error log, system table과 모든 업무 MyISAM table을 검사한다.
  4. crashed/corrupt table이 있으면 raw hold를 건드리지 말고 복제 working copy에서 repair 가능성을 검토한다. 복구 불가 table만 DB 솔루션 담당 절차로 행 단위 복구한다.
  5. 업무 사용자·GRANT는 확인하되 system DB를 다른 버전으로 덮어쓰지 않는다.
mariadb-check \

8.2 Scheduler 간섭 데이터 경계

🧒 아주 쉽게 설명하면: 8.2 Scheduler 간섭 데이터 경계

어떤 DB 행을 다시 넣고 어떤 행은 건드리지 않을지 선을 긋는 단계입니다.

Scheduler는 통계·배치 기록을 만들지만, CMS나 Master도 공용 상태를 바꿀 수 있습니다. 모든 table을 Scheduler 데이터라고 생각하면 업무 원본을 지울 수 있습니다.

A그룹은 승인된 Scheduler 전용 데이터라면 전량 교체하고, B그룹은 영향받은 후보 PK만 고칩니다. 그 외 업무 원본 table은 미러 상태를 유지합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Scheduler 실행 node, 실행 주기, job 이름, 대상 DB·Solr·Redis·Elasticsearch, 진행 중 job 목록입니다. Scheduler는 사람이 버튼을 누르지 않아도 시간에 맞춰 일하는 자동 직원입니다.

실제 흐름: source와 target의 자동 직원이 동시에 출근하지 않게 합니다. 진행 중 job이 끝났는지 확인하고 source Scheduler를 중지합니다. 리허설에서는 승인된 한 대만 제한 기동하고 배포·ES 로그 삭제 job은 별도 승인합니다.

  1. 실제 실행 node를 찾습니다.
  2. 진행 중·예약 job을 확인합니다.
  3. source Scheduler를 멈춥니다.
  4. target 한 대에서 필요한 job만 시험합니다.
  5. DB·검색·cache 변화를 비교합니다.

큰 위험: 101·102·103이 동시에 실행되면 같은 통계나 배포가 중복될 수 있습니다. 그래서 Scheduler는 전체 검증의 마지막에 한 대만 켭니다.

이 부분에서 확인할 것: 성공 기준: 대상 table 목록과 제외 table 목록에 담당자 승인.

8.3 Source B0/B1 data-only INSERT SQL

🧒 아주 쉽게 설명하면: 8.3 Source B0/B1 data-only INSERT SQL

source의 데이터를 ‘구조 없이 행만 넣는 SQL’로 준비하는 단계입니다.

data-only SQL은 CREATE TABLE 같은 구조 생성문보다 INSERT 문을 중심으로 만든 파일입니다. target의 구조는 먼저 준비되어 있다고 보고, 필요한 행을 넣는 데 사용합니다.

B0는 연습용, B1은 최종 전환 직전의 마지막 변경분입니다. 파일 이름과 생성 시각을 기록하고 SHA-256을 계산해 전송 중 변경되지 않았는지 확인합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: 원본의 현재 상태, 백업 저장 위치, 생성 시각, checksum, 복원 방법입니다. 백업은 파일 한 개를 복사하는 행동이 아니라 실패했을 때 돌아갈 지점을 만드는 일입니다.

B0와 B1: B0는 리허설 전 복원 연습용이고, B1은 최종 전환 직전 writer와 Scheduler를 멈춘 뒤 마지막 변경분을 고정하는 용도입니다. 이름이 비슷해도 시점과 목적이 다릅니다.

  1. 백업 대상을 정합니다.
  2. 파일·시각·크기를 기록합니다.
  3. SHA-256으로 변조 여부를 봅니다.
  4. target에서 실제 복원합니다.
  5. 성공·실패와 승인을 남깁니다.

초보자 원칙: ‘백업 성공’ 메시지만 믿지 말고 목록·checksum·복원 결과까지 확인합니다.

이 부분에서 확인할 것: 성공 기준: source 시각·범위·행 수·checksum·원복 SQL 기록.
  1. B0에는 미러 시작시각보다 충분히 앞선 B0_SAFE, 당시 예약대기 deploy ID, A/B table count·checksum·AUTO_INCREMENT를 기록한다. 기본 안전여유는 최소 2시간이며 미러 시작시각이 불확실하면 전날 00:00까지 넓혀 잡는다.
  2. B1에는 source Scheduler를 먼저 멈추고 진행 job 0건을 확인한다. B 공용 table 추출 동안 CMS/Master writer도 멈춰 같은 시점을 보장한다.
  3. master DB의 tbl_batch_log와 모든 활성 tenant DB의 9개 통계 table을 DB별 A그룹 data-only SQL로 만든다. 테스트베드처럼 같은 schema일 때만 합칠 수 있다. 파일은 SHA-256과 dump 종료코드가 있어야 한다.
mariadb-dump \
  --defaults-extra-file=<SOURCE_DB_OPTION_FILE> \
  --host="${SRC_DB_HOST}" --port="${SRC_DB_PORT}" \
  --no-create-info --complete-insert --skip-extended-insert \
  --skip-triggers --quick --lock-all-tables --hex-blob \
  --default-character-set=utf8mb4 --order-by-primary \
  --skip-add-locks --skip-disable-keys --skip-dump-date \
  "${TENANT_DB_NAME}" \
  tbl_api_statistics tbl_dialog_statistics \
  tbl_knowledge_statistics tbl_satisfaction_statistics \
  tbl_scenario_statistics tbl_scenario_node_statistics \
  tbl_slot_statistics tbl_top10_dialog_statistics tbl_user_statistics \
  > "${BACKUP_ROOT}/mariadb/${TENANT_DB_NAME}.B1.statistics.insert.sql"

mariadb-dump \
  --defaults-extra-file=<SOURCE_DB_OPTION_FILE> \
  --host="${SRC_DB_HOST}" --port="${SRC_DB_PORT}" \
  --no-create-info --complete-insert --skip-extended-insert \
  --skip-triggers --quick --lock-all-tables --hex-blob \
  --default-character-set=utf8mb4 --order-by-primary \
  --skip-add-locks --skip-disable-keys --skip-dump-date \
  "${MASTER_DB_NAME}" tbl_batch_log \
  > "${BACKUP_ROOT}/mariadb/${MASTER_DB_NAME}.B1.batch-log.insert.sql"

sha256sum "${BACKUP_ROOT}/mariadb/"*.B1.*.insert.sql

B그룹 후보는 source와 target 양쪽에서 B0_SAFE ≤ created_at/modified_at/finished_at/request_date < B1인 PK, B0 예약대기 deploy ID와 그 bot/deploy 연관 PK를 뽑아 합집합으로 만든다. source 목록만 쓰면 target Scheduler가 만든 행을 놓치므로 금지한다. 검증된 숫자 PK 목록을 --where="id IN (...)"으로 추출하며, source에서 삭제된 후보는 INSERT 파일에 없다는 점을 manifest에 표시한다.

-- source와 target 양쪽에서 실행한 뒤 PK 합집합을 승인한다.
SELECT id FROM tbl_learn_recommend
 WHERE (created_at  >= :B0_SAFE AND created_at  < :B1)
    OR (modified_at >= :B0_SAFE AND modified_at < :B1)
    OR (request_date >= :B0_SAFE AND request_date < :B1);

SELECT id, bot_id FROM tbl_deploy
 WHERE deploy_type = 'SCHEDULE'
   AND (id IN (:B0_PENDING_DEPLOY_IDS)
        OR (created_at >= :B0_SAFE AND created_at < :B1)
        OR (modified_at >= :B0_SAFE AND modified_at < :B1)
        OR (finished_at >= :B0_SAFE AND finished_at < :B1)
        OR (deploy_time >= :B0_SAFE AND deploy_time < :B1));

SELECT id, deploy_id FROM tbl_manage_deploy
 WHERE deploy_id IN (:DEPLOY_ID_UNION)
    OR (created_at >= :B0_SAFE AND created_at < :B1)
    OR (modified_at >= :B0_SAFE AND modified_at < :B1);

8.4 Target 데이터 비우기·재적재

🧒 아주 쉽게 설명하면: 8.4 Target 데이터 비우기·재적재

target에서 승인된 범위의 오래된 행을 치우고 source 행을 넣는 단계입니다.

‘데이터를 비운다’는 말은 DB 전체를 지운다는 뜻이 아닙니다. 승인된 A그룹 table 또는 특정 범위만 대상으로 합니다. target 식별을 확인한 뒤 preclear 백업과 원복 SQL이 있어야 합니다.

MyISAM에서는 중간에 실패해도 자동으로 되돌아가지 않을 수 있으므로, 적용 전후 행 수와 checksum을 비교합니다. 실패하면 미리 만든 rollback INSERT SQL로 되돌립니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source VM의 CPU·RAM·디스크·NIC·OS·서비스와 target host의 저장공간·네트워크·자원입니다. VM은 가상 CPU·메모리·디스크·네트워크 카드를 가진 컴퓨터입니다.

실제 흐름: 가상화 담당자가 VM을 복사하거나 export/import합니다. 복사본을 처음 켤 때는 원본과 다른 임시 IP·hostname을 사용합니다. 부팅 후 OS·mount·/data·자동기동 서비스·Scheduler 상태를 확인합니다.

  1. source 상태와 백업을 고정합니다.
  2. target 저장소와 network를 확인합니다.
  3. VM을 복사·인수합니다.
  4. 임시 주소로 격리 부팅합니다.
  5. 원본과 충돌이 없는지 확인합니다.

비유: VM 복사는 집 전체를 새 동네에 복사하는 일입니다. 주소판과 전화번호가 예전 집과 같으면 우편과 전화가 섞이므로, 새 주소를 붙이고 손님을 받기 전까지 격리합니다.

이 부분에서 확인할 것: 변경 전 필수: target 확인, writer 정지, preclear 백업, 승인.
  1. target Scheduler와 모든 application writer를 중지하고 대상 DB의 hostname/IP/schema를 다시 확인한다.
  2. master의 batch log와 각 tenant의 9개 통계 table에 있는 target 현 데이터를 같은 data-only 형식의 DB별 target-preclear.rollback.insert.sql로 추출하고 SHA-256·count·checksum을 기록한다.
  3. B1 INSERT SQL을 격리 staging DB의 동일 DDL table에 먼저 적재해 문법, row count, PK/unique 중복, CHECK TABLE과 source checksum을 검증한다.
  4. 각 대상 DB의 한 client session에서 그 DB의 A그룹 table을 WRITE lock하고 명시적 DELETE FROM으로 데이터만 비운 뒤 해당 B1 SQL을 적재한다. 실패하면 writer를 계속 정지하고 그 DB의 rollback INSERT SQL로 원복한다.
  5. 각 table의 AUTO_INCREMENT를 source B1 manifest 값 이상으로 맞춘 뒤 count·checksum을 즉시 비교한다.

아래 묶음 SQL은 master와 tenant가 같은 meritz_easycms인 현 테스트베드용 예시다. 운영에서 DB가 분리되어 있으면 master에는 tbl_batch_log만, 각 tenant에는 9개 통계 table만 따로 lock·delete·import한다.

LOCK TABLES
  tbl_batch_log WRITE, tbl_api_statistics WRITE,
  tbl_dialog_statistics WRITE, tbl_knowledge_statistics WRITE,
  tbl_satisfaction_statistics WRITE, tbl_scenario_statistics WRITE,
  tbl_scenario_node_statistics WRITE, tbl_slot_statistics WRITE,
  tbl_top10_dialog_statistics WRITE, tbl_user_statistics WRITE;

DELETE FROM tbl_batch_log;
DELETE FROM tbl_api_statistics;
DELETE FROM tbl_dialog_statistics;
DELETE FROM tbl_knowledge_statistics;
DELETE FROM tbl_satisfaction_statistics;
DELETE FROM tbl_scenario_statistics;
DELETE FROM tbl_scenario_node_statistics;
DELETE FROM tbl_slot_statistics;
DELETE FROM tbl_top10_dialog_statistics;
DELETE FROM tbl_user_statistics;

SOURCE /secure/<validated-B1-file-for-this-DB>.insert.sql;
UNLOCK TABLES;

위 SQL은 대상 DB별 실행 템플릿이다. SOURCE가 같은 client session 안에서 성공했는지 확인하며, MyISAM에는 transaction rollback이 없으므로 중간 실패를 ROLLBACK으로 복구할 수 없다.

8.5 공용 상태 B그룹 선택 교정

🧒 아주 쉽게 설명하면: 8.5 공용 상태 B그룹 선택 교정

업무 원본을 보존하면서 정말 영향을 받은 행만 고치는 단계입니다.

B그룹은 Scheduler뿐 아니라 CMS·Master·사용자 요청도 함께 만질 수 있는 공용 상태입니다. 그래서 전체 삭제 후 재적재하면 안 되고, source와 target의 후보 PK를 비교해 필요한 행만 교정합니다.

후보 PK는 ‘이 행이 달라졌을 가능성이 있다’는 목록이지 무조건 지워도 된다는 뜻이 아닙니다. 각 PK의 before/after 값을 기록하고 DB 담당자의 승인을 받습니다.

이 부분에서 확인할 것: NO-GO: 후보 범위가 정해지지 않았거나 before-image가 없음.
  1. 후보 PK 합집합의 target 원본 행을 table별 rollback SQL 또는 backup table에 먼저 저장한다.
  2. tbl_manage_deploy, tbl_learn_recommend, tbl_deploy의 후보 PK만 target에서 삭제하고 source B1에 실제 존재하는 후보 행만 INSERT한다. source에 없는 후보는 삭제 상태로 남긴다.
  3. tbl_bot은 행 전체를 교체하지 않는다. 후보 bot의 active_deploy_id, active_learn_id, standby_deploy_id, standby_learn_id와 대응 수정정보만 source staging 값으로 UPDATE한다.
  4. 각 명령의 예상/실제 affected rows를 비교하고 다르면 즉시 중단한다. MyISAM이므로 실패 시 준비된 target before-image로 역순 원복한다.

8.6 검증·기동 제한

🧒 아주 쉽게 설명하면: 8.6 검증·기동 제한

DB를 확인한 뒤 애플리케이션을 아주 제한적으로 연결하는 단계입니다.

먼저 DB 자체가 맞는지 확인하고, 그 다음 Master·Engine 같은 프로그램을 붙입니다. Scheduler는 여러 VM에서 동시에 실행되지 않도록 마지막까지 꺼 둡니다.

리허설에서는 101 한 대만 승인된 job을 제한적으로 실행하고 결과를 비교합니다. target에서 만든 시험 이력이 최종 운영 DB에 섞이지 않도록 처리합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: DB·Redis·검색 서비스 health 결과, JAR, 환경변수, 설정파일, 실행 사용자, 서비스 의존관계입니다. 애플리케이션은 다른 서비스에 전화를 거는 프로그램입니다.

실제 흐름: 데이터 서비스가 준비된 뒤 Master·Engine·Gateway·CMS·Chat UI를 연결합니다. 각 서비스마다 프로세스·port·API·로그를 확인하고 source 주소를 보고 있지 않은지 검색합니다.

  1. 파일과 설정 주소를 확인합니다.
  2. 의존 서비스가 정상인지 봅니다.
  3. 한 서비스씩 기동합니다.
  4. API와 업무 흐름을 검증합니다.

기억할 점: systemctl active는 1차 신호일 뿐입니다. 실제 성공은 API·연결·로그인·검색·시뮬레이터까지 확인해야 합니다.

이 부분에서 확인할 것: 성공 기준: DB 정합성 승인, Scheduler 중복 없음, 주요 읽기·검색 업무 통과.
  • A그룹은 source/target의 count, MIN/MAX PK, AUTO_INCREMENT, checksum, unique 중복, CHECK TABLE이 일치한다.
  • B그룹은 후보 PK별 source/target 행과 deploy 결과·완료시각, manage deploy, learn recommend, bot의 네 상태 컬럼이 일치한다.
  • A/B 이외 table의 전후 count·checksum이 동일하다. 차이가 있으면 “Scheduler 간섭 데이터만 변경” 조건 실패다.
  • tbl_deploy.bot_id → tbl_bot.id, learning 정보, bot active/standby deploy·learn, tenant tbl_manage_deploy.deploy_id의 논리 orphan이 없다.
  • 기한이 지난 STANDBY/SCHEDULE 예약배포를 전수 확인하고 업무 승인 전 Scheduler를 기동하지 않는다.
DB 정합화 전 애플리케이션 선기동 금지 master의 초기화 코드와 CMS의 schema update, Scheduler의 batch 초기화가 DB를 변경할 수 있다. 최초 검증에서는 승인된 외부 override로 DDL 자동 변경과 Quartz 자동 시작을 막고, 선택 재적재·검증이 끝난 뒤에만 정상 설정으로 전환한다.

9. Redis 5.0.8 재클러스터링·cache 재배포

🧒 아주 쉽게 설명하면: 9. Redis 5.0.8 재클러스터링·cache 재배포

빠른 임시 창고인 Redis를 target에서 정상화하는 단계입니다.

Redis에는 세션·cache·큐처럼 다시 만들 수 있는 값이 있을 수 있지만, 실제 업무에서 무엇을 저장하는지는 설정을 확인해야 합니다. 여러 Redis가 하나의 cluster라면 node와 slot 관계도 같이 맞아야 합니다.

기존 cluster가 target에서 안전하게 재결합되면 그 경로를 사용하고, 상태가 꼬이면 새 빈 cluster를 만들고 애플리케이션의 배포 기능으로 cache를 재생성합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Redis 노드의 주소·port·master/replica 역할·node ID·slot 상태와 AOF/RDB 파일 정보입니다. Redis가 cache만 저장하는지, 로그인 세션·queue·업무 상태도 저장하는지는 애플리케이션 설정으로 확인합니다.

실제 흐름: PONG은 한 노드가 대답했다는 뜻이고, cluster_state:ok와 모든 slot 정상은 집단 전체가 일할 준비가 됐다는 뜻입니다. 기존 cluster 재결합이 안전하면 유지하고, 주소·node ID·slot이 꼬이면 빈 3 master/3 replica를 구성한 뒤 cache를 다시 만듭니다.

  1. 노드와 역할을 기록합니다.
  2. source와 target이 동시에 같은 cluster가 되지 않게 합니다.
  3. 재결합 또는 새 cluster 중 하나를 선택합니다.
  4. cache 재생성 뒤 TTL·대표 기능을 확인합니다.

주의: ‘Redis니까 지워도 된다’가 아닙니다. cache라면 다시 만들 수 있지만 세션·queue라면 초기화가 곧 업무 영향일 수 있으므로 담당자 승인이 필요합니다.

이 부분에서 확인할 것: 금지: source와 target을 같은 cluster에 무검증으로 섞기, source에서 FLUSHALL.
Redis 데이터 이관 없음 Redis는 재생성 가능한 cache이므로 source에서 B0/B1 RDB를 별도로 옮겨 import하지 않는다. 미러본의 cluster state·AOF·RDB가 정상이라면 그대로 재결합할 수 있고, 그렇지 않으면 빈 cluster를 만든 뒤 시스템 배포 기능으로 cache를 재생성한다.

9.1 파일과 금지 조합

🧒 아주 쉽게 설명하면: 9.1 파일과 금지 조합

Redis 파일을 어떤 식으로 다룰지 정하는 안전장치입니다.

RDB는 특정 시점의 메모리 저장 파일이고 AOF는 명령 기록에 가까운 파일입니다. cluster state와 설정이 서로 다른 시점이면 파일을 함께 넣었을 때 노드가 이상해질 수 있습니다.

따라서 파일을 발견했다고 target에 바로 덮어쓰지 않고, 경로·생성 시각·checksum을 보관한 후 재결합 또는 새 cluster 판단을 합니다.

이 부분에서 확인할 것: 금지: 서로 다른 시점의 RDB/AOF/cluster state를 섞어 무검증 기동.
  • 정적 설정은 /application/redis/conf/7000.conf, 7001.conf다.
  • Redis가 자동 관리하는 cluster state는 각 data directory의 /application/redis/db/7000/7000.conf, /application/redis/db/7001/7001.conf다. 같은 파일명이어도 정적 설정과 혼동하거나 직접 편집하지 않는다.
  • 각 data directory의 appendonly.aof, dump.rdb와 자동 cluster state를 한 세트로 취급한다. 현재 appendonly yes이므로 재기동 시 AOF가 RDB보다 우선될 수 있다.
  • cluster state만 지우고 AOF/RDB를 남기는 방식은 금지한다. 새 node ID의 non-empty master가 되어 표준 --cluster create, reset·replica 전환이 막힐 수 있다.

9.4 시스템 배포 기능으로 cache 재생성

🧒 아주 쉽게 설명하면: 9.4 시스템 배포 기능으로 cache 재생성

빈 Redis에 애플리케이션이 필요한 값을 다시 만들어 넣는 단계입니다.

Redis를 복원했다는 말은 모든 예전 cache 값을 그대로 가져왔다는 뜻이 아니라, 업무 시스템이 다시 실행되면서 필요한 값을 재생성했다는 뜻일 수 있습니다.

재생성 뒤 대표 화면·로그인·검색·챗봇 등 실제 사용 흐름에서 cache miss가 오류로 이어지지 않는지 확인합니다.

이 부분에서 확인할 것: 성공 기준: 대표 cache 조회, TTL, 애플리케이션 로그, 시뮬레이터 결과 정상.
  1. Scheduler는 계속 OFF로 두고 DB·Solr·Elasticsearch 최종 복원 및 관련 애플리케이션의 내부 health 검증을 먼저 끝낸다.
  2. 승인된 시스템 배포 기능으로 전체 bot/cache를 한 번만 재배포한다. 실행 ID, 대상 bot, 시작·종료 시각과 성공/실패를 기록한다.
  3. 재배포 기능이 stale key 삭제 없이 upsert만 수행한다면 기존 persistence 유지 경로를 합격 처리하지 않는다. 9.3의 빈 cluster에서 다시 배포한다.
  4. 대표 cache key의 type/value/TTL, cluster-aware read/write, 각 master의 key 분산, replica 동기화와 애플리케이션 조회를 확인한다.

11. Elasticsearch 7.8.0 / Kibana 7.8.0 재클러스터링·Snapshot 복원

검색·분석 시스템을 새 cluster로 만들고 Snapshot을 읽어오는 단계입니다.

Elasticsearch는 node와 shard가 있는 검색 저장소입니다. node data 폴더를 통째로 복사하면 cluster UUID·shard 상태·버전 문제를 만들 수 있으므로 새 빈 cluster를 만들고 공식 Snapshot을 복원합니다.

Kibana 화면도 index와 연결 설정이 필요합니다. Elasticsearch 데이터와 정책 객체를 각각 확인하고, target에서 source로 쓰는 연결이 없는지 검사합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Elasticsearch node·cluster 정보, index·shard·alias 목록, Snapshot repository, template·pipeline·ILM·SLM 정책입니다. Elasticsearch는 index를 여러 shard로 나누어 저장하므로 data 폴더를 일반 파일처럼 복사하지 않습니다.

실제 흐름: target에서 새 빈 cluster를 준비하고 repository를 등록한 뒤 성공한 Snapshot을 restore합니다. 복원 후 cluster health·node·index·shard를 보고, 정책 객체는 별도로 비교합니다. green은 shard 배치가 정상이라는 뜻이지 업무 검색까지 자동 보장한다는 뜻은 아닙니다.

  1. 새 cluster와 repository를 준비합니다.
  2. 필요한 snapshot과 index를 복원합니다.
  3. template·pipeline·ILM·SLM을 따로 확인합니다.
  4. 대표 검색·정렬·aggregation·재기동을 시험합니다.

raw data 폴더를 피하는 이유: 그 안에는 cluster UUID와 shard 상태 같은 내부 정보가 들어 있어 버전·노드·시점이 맞지 않으면 cluster가 깨질 수 있습니다.

이 부분에서 확인할 것: 성공 기준: cluster green 목표, failed/unassigned shard 0, 필요한 index·alias·정책 복원.
미러 data는 보관본, 복구 원본은 Snapshot 노드별 /application/elk/data 복사는 cluster 일관성을 보장하지 않는다. target에서는 미러 data를 삭제하지 않고 hold로 옮긴 뒤 빈 working data로 새 cluster를 만들고, 완료된 Elasticsearch Snapshot만 restore한다.

11.3 Repository·정책 객체 수동 이관

🧒 아주 쉽게 설명하면: 11.3 Repository·정책 객체 수동 이관

Snapshot 창고 주소와 자동 관리 규칙을 target에도 등록하는 단계입니다.

repository는 snapshot 파일이 있는 장소입니다. ILM은 오래된 index를 정리하는 규칙이고 SLM은 snapshot을 자동으로 찍는 규칙입니다. 데이터만 복원하고 규칙을 잊으면 target이 예기치 않게 삭제·백업 작업을 할 수 있습니다.

이 부분에서 확인할 것: 성공 기준: 정책 ID·내용·실행 주체·다음 실행 여부가 승인된 상태.

  2. source export에서 ingest pipeline, ILM policy, component template, composable template, legacy template 순으로 target에 ID별 PUT한다. API 응답의 통계·수정시각·version wrapper는 PUT body에서 제거한다.
  3. node 이름을 기준으로 한 allocation 조건, source 전용 path·주소·read-only block을 제거하고 object 이름·개수·핵심 JSON을 source와 비교한다.
  4. SLM은 repository와 restore가 검증될 때까지 import·시작하지 않는다.

11.5 ILM·SLM 안전 검증

🧒 아주 쉽게 설명하면: 11.5 ILM·SLM 안전 검증

자동 삭제와 자동 백업이 target에서 안전한지 시험하는 단계입니다.

ILM이 잘못 켜지면 오래된 index를 삭제할 수 있고, SLM이 잘못 켜지면 target에서 snapshot을 찍거나 source용 repository를 건드릴 수 있습니다.

리허설 중에는 자동 실행을 제한하고, 정책 explain/API와 로그로 실제 대상·조건·권한을 확인합니다.

이 부분에서 확인할 것: 성공 기준: target에서 의도하지 않은 삭제·snapshot·source 접근이 없음.
  1. 복원 index는 원래 creation/rollover 시각과 index.lifecycle.name을 보유할 수 있다. ILM 시작 전에 모든 관리 index의 _ilm/explain을 확인해 현재 phase/age/action과 즉시 delete·rollover·allocation 가능성을 승인한다.
  2. ILM policy 이름, rollover alias, template 연결과 target tier/node attribute가 유효한지 확인한다. 잘못된 allocation 조건은 시작 전에 수정한다.
  3. 복원용 ol_migration_repo는 read-only로 유지한다. SLM에는 target만 write하는 별도 <TARGET_SLM_REPOSITORY>를 등록·verify한다. 동일 저장소를 넘겨받아야 한다면 source의 write 접근을 완전히 제거한 후에만 target에 단독 write 권한을 준다.
  4. SLM policy는 source export의 각 policy 객체만 PUT한다. repository를 <TARGET_SLM_REPOSITORY>로 바꾸고 snapshot 이름·index 목록·schedule·retention을 검토한 뒤 시험 snapshot 한 건을 실행한다.
  5. SLM retention이 이관용 snapshot을 삭제하지 않도록 migration repository와 runtime SLM repository를 분리한다.
  6. 모든 검증과 승인이 끝난 뒤에만 ILM, SLM 순서로 시작하고 status와 최근 실행 결과를 확인한다.
PUT /_slm/policy/<SLM_POLICY_ID>
{
  "schedule": "<APPROVED_CRON>",
  "name": "<APPROVED_SNAPSHOT_NAME_PATTERN>",
  "repository": "<TARGET_SLM_REPOSITORY>",
  "config": { "indices": ["<APPROVED_INDEX_PATTERN>"] },
  "retention": { "expire_after": "<APPROVED_RETENTION>" }
}
GET  /<RESTORED_INDEX_PATTERN>/_ilm/explain
GET  /_ilm/policy
GET  /_slm/policy
# TARGET_SLM_REPOSITORY는 target 단독 writer여야 한다.
POST /_ilm/start
POST /_slm/start

12. 애플리케이션·Scheduler 기동

🧒 아주 쉽게 설명하면: 12. 애플리케이션·Scheduler 기동

서비스들을 서로 의존하는 순서대로 켜는 단계입니다.

Master·Engine·Gateway·CMS는 혼자서 완성되는 프로그램이 아닙니다. DB·Redis·검색 시스템을 먼저 준비하고, 애플리케이션이 올바른 주소를 보도록 한 뒤 화면과 업무 흐름을 확인합니다.

Scheduler는 다른 서비스와 DB를 자동으로 바꿀 수 있으므로 마지막에 한 대만 제한적으로 켭니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Scheduler 실행 node, 실행 주기, job 이름, 대상 DB·Solr·Redis·Elasticsearch, 진행 중 job 목록입니다. Scheduler는 사람이 버튼을 누르지 않아도 시간에 맞춰 일하는 자동 직원입니다.

실제 흐름: source와 target의 자동 직원이 동시에 출근하지 않게 합니다. 진행 중 job이 끝났는지 확인하고 source Scheduler를 중지합니다. 리허설에서는 승인된 한 대만 제한 기동하고 배포·ES 로그 삭제 job은 별도 승인합니다.

  1. 실제 실행 node를 찾습니다.
  2. 진행 중·예약 job을 확인합니다.
  3. source Scheduler를 멈춥니다.
  4. target 한 대에서 필요한 job만 시험합니다.
  5. DB·검색·cache 변화를 비교합니다.

큰 위험: 101·102·103이 동시에 실행되면 같은 통계나 배포가 중복될 수 있습니다. 그래서 Scheduler는 전체 검증의 마지막에 한 대만 켭니다.

이 부분에서 확인할 것: 성공 기준: 각 서비스 health와 로그 정상, 중복 Scheduler 없음.

12.1 첫 기동 전

전원을 켜기 전에 마지막으로 확인하는 단계입니다.

target hostname·IP·설정파일·환경변수·실행 사용자·자동기동 여부를 확인합니다. source 주소가 설정에 남아 있으면 target 서비스가 원본 DB나 검색 cluster에 접속할 수 있습니다.

기동 전에 서비스별 의존 대상과 포트를 적어 두고, 실패하면 status와 journal을 저장합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: DB·Redis·검색 서비스 health 결과, JAR, 환경변수, 설정파일, 실행 사용자, 서비스 의존관계입니다. 애플리케이션은 다른 서비스에 전화를 거는 프로그램입니다.

  1. 파일과 설정 주소를 확인합니다.
  2. 의존 서비스가 정상인지 봅니다.
  3. 한 서비스씩 기동합니다.
  4. API와 업무 흐름을 검증합니다.

이 부분에서 확인할 것: 멈춤 기준: source endpoint가 남아 있거나 target 격리가 확인되지 않음.
  • 모든 설정의 DB/Redis/ZK/Solr/ES URL이 격리된 target을 가리키며 source IP나 운영 VIP가 남지 않았다.
  • 복원된 DB의 tbl_manage_schema.prefix_url, schema_name, user_name과 tbl_manage_tenant.manage_schema_id를 전수 확인했다. tenant 접속지는 YAML이 아니라 이 테이블에서 동적으로 조립되므로 source 주소가 하나라도 남으면 기동 금지한다.
  • ibot.cms.domain, master.api.url, Engine URL과 target VM의 outbound ACL을 확인해 원본 DB·서비스로의 egress를 차단했다.
  • JAR 파일명과 checksum이 미러 직전 VM manifest와 일치한다.
  • profile은 tc,core-tc이며 로그는 각 /logs/<module> 아래로 기록된다.
  • master/CMS 첫 검증 기동은 schema 변경을 막기 위해 ddl-auto=none 또는 validate override가 적용됐다.
  • OS와 JVM의 timezone이 모두 Asia/Seoul인지 확인했다. Quartz cron은 timezone을 별도 지정하지 않고 코드가 LocalDate/LocalDateTime.now()를 사용한다.
  • L4/VIP에 target이 아직 등록되지 않았고 테스트 호출이 외부 시스템으로 나가지 않는다.

Scheduler 고위험 job RESERVE_DEPLOY_JOB은 매분 예약 배포를 찾아 CMS를 호출하고 DB·Solr active/standby·Redis cache·Engine 알림까지 바꿀 수 있다. ES_LOG_BACKUP_JOB은 ES snapshot 생성 후 보존기간이 지난 index를 삭제할 수 있다. target endpoint 격리와 승인 없이 Scheduler 전체를 켜지 않는다.

12.3 Scheduler 제한 시험

🧒 아주 쉽게 설명하면: 12.3 Scheduler 제한 시험

자동 작업을 아주 작은 범위에서 시험하는 단계입니다.

Scheduler는 정해진 시간마다 통계 생성, 배포, 로그 백업 등을 할 수 있습니다. 101·102·103이 모두 켜지면 같은 작업이 중복 실행될 수 있습니다.

리허설에서는 승인된 한 VM의 Scheduler만 켜고, 위험한 배포·삭제 job은 비활성으로 둡니다. 실행 전후 DB·Solr·ES·Redis와 로그를 비교합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Scheduler 실행 node, 실행 주기, job 이름, 대상 DB·Solr·Redis·Elasticsearch, 진행 중 job 목록입니다. Scheduler는 사람이 버튼을 누르지 않아도 시간에 맞춰 일하는 자동 직원입니다.

실제 흐름: source와 target의 자동 직원이 동시에 출근하지 않게 합니다. 진행 중 job이 끝났는지 확인하고 source Scheduler를 중지합니다. 리허설에서는 승인된 한 대만 제한 기동하고 배포·ES 로그 삭제 job은 별도 승인합니다.

  1. 실제 실행 node를 찾습니다.
  2. 진행 중·예약 job을 확인합니다.
  3. source Scheduler를 멈춥니다.
  4. target 한 대에서 필요한 job만 시험합니다.
  5. DB·검색·cache 변화를 비교합니다.

큰 위험: 101·102·103이 동시에 실행되면 같은 통계나 배포가 중복될 수 있습니다. 그래서 Scheduler는 전체 검증의 마지막에 한 대만 켭니다.

이 부분에서 확인할 것: 성공 기준: 한 대만 실행, 진행 중 job 없음, 예상 범위의 데이터만 변경.
  1. spring.quartz.auto-startup=false를 적용한 별도 시험 설정으로 자동 cron을 막고 101 한 대에서만 프로세스를 올린다. spring.batch.job.enabled=false만으로 Quartz cron이 멈춘다고 가정하지 않는다.
  2. 읽기·파생 통계 job 한 개를 격리 데이터로 수동 실행한다. 예약 배포와 ES log backup은 리허설 승인 전 실행 금지한다.
  3. 실행 전후 DB/ES/Solr/Redis count와 tbl_batch_log 한 건의 시작·종료·상태를 기록한다.
  4. 수동 /executeScheduler는 job별 멱등성과 코드 매핑이 확인된 범위에만 쓴다. 현재 seed에는 소스에 없는 AnswerLink 계열 클래스도 있어 ClassNotFound 가능성이 있다.
  5. learn recommend는 수동 from/to를 읽지 않고 중복 insert 가능성이 있다. dialog/satisfaction 통계도 bulk insert/unique 충돌 위험이 있어 자동 보정하지 않는다. Knowledge 통계의 여러 날짜 보정은 날짜 증가 로직 위험 때문에 반드시 1일 단위로 실행·대조한다.
  6. 시험이 끝나면 Scheduler를 다시 끄고 B1 완료 때까지 정지 상태를 유지한다.

ES_LOG_BACKUP_JOB은 실패 상태를 만들더라도 종료부에서 성공으로 덮을 수 있는 코드 경로가 확인됐다. 따라서 tbl_batch_log의 성공 표시만 믿지 말고 Elasticsearch _snapshot API의 실제 snapshot 상태와 ES 로그를 직접 확인한다.

14. B1 — 최종 데이터 동기화

🧒 아주 쉽게 설명하면: 14. B1 — 최종 데이터 동기화

운영 전환 직전에 마지막 변경분을 맞추는 단계입니다.

B0 리허설 이후에도 source에서 새 문서·통계·배치 기록이 생길 수 있습니다. B1은 신규 요청과 writer를 멈춘 뒤 마지막 순간의 데이터를 고정하는 백업입니다.

B1이 끝난 뒤 target을 다시 검증하고, 그 다음에만 운영 트래픽을 target으로 보냅니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: 원본의 현재 상태, 백업 저장 위치, 생성 시각, checksum, 복원 방법입니다. 백업은 파일 한 개를 복사하는 행동이 아니라 실패했을 때 돌아갈 지점을 만드는 일입니다.

B0와 B1: B0는 리허설 전 복원 연습용이고, B1은 최종 전환 직전 writer와 Scheduler를 멈춘 뒤 마지막 변경분을 고정하는 용도입니다. 이름이 비슷해도 시점과 목적이 다릅니다.

  1. 백업 대상을 정합니다.
  2. 파일·시각·크기를 기록합니다.
  3. SHA-256으로 변조 여부를 봅니다.
  4. target에서 실제 복원합니다.
  5. 성공·실패와 승인을 남깁니다.

초보자 원칙: ‘백업 성공’ 메시지만 믿지 말고 목록·checksum·복원 결과까지 확인합니다.

이 부분에서 확인할 것: 멈춤 기준: writer 정지와 진행 중 job 0건이 확인되지 않으면 B1을 만들지 않음.

MariaDB는 미러 DB 전체를 유지하고 A그룹 data-only INSERT SQL과 B그룹 영향 PK만 동기화한다. Redis 데이터는 동기화하지 않고 정상 cluster 위에 cache를 재배포한다. Solr는 모든 collection의 B1 BACKUP/RESTORE, Elasticsearch는 B1 Snapshot/Restore와 정책 객체의 명시적 이관을 수행한다.

14.1 최종 쓰기 중지

🧒 아주 쉽게 설명하면: 14.1 최종 쓰기 중지

source에서 데이터가 더 변하지 않도록 잠시 멈추는 단계입니다.

사용자 요청과 Scheduler가 계속 들어오면 source와 target의 데이터가 서로 달라집니다. 그래서 점검창 동안 신규 요청을 막고, 진행 중 작업이 끝났는지 확인합니다.

서비스를 막는 순서와 읽기 전용 전환 여부는 운영 담당자가 결정합니다. 강제 종료보다 정상 완료·writer 차단을 우선합니다.

이 부분에서 확인할 것: 성공 기준: Scheduler·writer 정지, 진행 중 job 없음, 중단 시각 기록.
  1. L4에서 신규 사용자 쓰기를 차단하고 업무 점검창을 시작한다. T_FINAL을 기록한다.
  2. source Scheduler를 가장 먼저 중지한다. 진행 중 job이 끝났는지 애플리케이션 로그와 tbl_batch_log.batch_enddt IS NULL 조회로 확인한다.
  3. source gateway/CMS/master/engine/chat-ui 등 모든 writer를 중지하거나 read-only로 만든다.
  4. 예약 배포 대기·진행 상태, 학습/배포 작업, ES snapshot 작업이 진행 중이 아닌지 업무 테이블과 로그에서 확인한다.
  5. 예약 배포 조회 결과가 있으면 Scheduler 재기동 직후 실행될 수 있으므로 목록을 업무 담당자에게 승인받고, 미승인 건이 있으면 계속 정지한다.
  6. DB/Solr/ES에서 2회 연속 count/position을 확인해 쓰기가 멈췄음을 기록한다. Redis는 cache 기준 건수만 채증하며 최종 동기화 기준으로 쓰지 않는다.

14.2 B1 최종 선택 백업

🧒 아주 쉽게 설명하면: 14.2 B1 최종 선택 백업

마지막 백업 묶음을 만드는 단계입니다.

MariaDB는 승인된 선택 범위의 INSERT SQL, Solr는 모든 collection BACKUP, Elasticsearch는 index Snapshot과 정책 export를 만듭니다. 제품마다 안전한 백업 방법이 다릅니다.

파일명·생성 시각·checksum·완료 상태를 기록합니다. 백업 하나라도 실패하면 운영 전환하지 않습니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: 원본의 현재 상태, 백업 저장 위치, 생성 시각, checksum, 복원 방법입니다. 백업은 파일 한 개를 복사하는 행동이 아니라 실패했을 때 돌아갈 지점을 만드는 일입니다.

B0와 B1: B0는 리허설 전 복원 연습용이고, B1은 최종 전환 직전 writer와 Scheduler를 멈춘 뒤 마지막 변경분을 고정하는 용도입니다. 이름이 비슷해도 시점과 목적이 다릅니다.

  1. 백업 대상을 정합니다.
  2. 파일·시각·크기를 기록합니다.
  3. SHA-256으로 변조 여부를 봅니다.
  4. target에서 실제 복원합니다.
  5. 성공·실패와 승인을 남깁니다.

초보자 원칙: ‘백업 성공’ 메시지만 믿지 말고 목록·checksum·복원 결과까지 확인합니다.

이 부분에서 확인할 것: NO-GO: 일부 collection/index만 백업되었거나 snapshot failed shard가 있음.
  1. MariaDB A그룹만 data-only·complete INSERT 형식으로 추출하고 B그룹의 source/target 후보 PK 합집합, source 후보행 SQL, count/checksum/AUTO_INCREMENT manifest를 만든다. 전체 DB dump는 하지 않는다.
  2. Redis는 B1 RDB/AOF를 이관하지 않는다. 현재 cluster topology와 key count는 참고 증적으로만 남긴다.
  3. Solr의 source collection 이름을 다시 전수 조회하고 모든 collection에 hard commit 후 새 이름으로 BACKUP한다. configset/alias/count와 비동기 completed 결과를 collection별로 남긴다.
  4. Elasticsearch의 ILM/SLM을 중지하고 기존 status를 기록한다. 정책·template·pipeline·settings를 다시 export한 뒤 include_global_state:true인 final snapshot을 만들고 SUCCESS/failed shard 0/index 목록을 확인한다.
  5. 노드별 CMS upload 등 파일성 데이터를 다시 archive/checksum한다.

모든 B1 산출물의 종료 시각과 checksum이 확정될 때까지 source를 변경·재기동하거나 L4를 target으로 넘기지 않는다. 전환이 취소되면 source의 ILM/SLM을 기존 status로 되돌린다.

14.3 MariaDB R1 선택 재적재

🧒 아주 쉽게 설명하면: 14.3 MariaDB R1 선택 재적재

최종 고정된 source 데이터를 target DB에 적용하는 단계입니다.

R1은 B1을 target에 반영한 결과입니다. A그룹은 승인된 전량 교체, B그룹은 후보 PK 선택 교정, 그 외 업무 원본은 보존합니다.

적용 후 source와 target의 count·checksum·기본키·AUTO_INCREMENT·논리 orphan을 비교합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: source DB의 현재 데이터, target DB의 table 구조, Scheduler가 건드리는 table 목록, 그리고 승인된 적용 범위입니다. DB는 단순한 파일 창고가 아니라 여러 프로그램이 계속 읽고 쓰는 업무 장부이므로, ‘파일이 복사됐나’보다 ‘어떤 행이 같은가’를 확인합니다.

실제 흐름: 먼저 읽기 명령으로 접속·table·행 수·진행 중 작업을 확인합니다. 그다음 writer와 Scheduler를 멈추고 source에서 승인된 data-only INSERT SQL을 만듭니다. target에서는 승인된 범위만 preclear하고 INSERT한 뒤 source와 count·기본키·checksum을 비교합니다. 나머지 업무 원본 table은 건드리지 않는 것이 기본입니다.

  1. 읽기: DB가 살아 있고 구조가 맞는지 봅니다.
  2. 고정: 더 이상 행이 변하지 않도록 writer를 멈춥니다.
  3. 적용: A그룹 전량 또는 B그룹 후보 PK만 처리합니다.
  4. 비교: 다르면 성공으로 보지 않고 멈춥니다.

가장 중요한 이유: MyISAM에서는 실패하면 DB가 자동으로 원래 상태로 돌아온다고 가정하면 안 됩니다. 따라서 지우기 전에 before-image와 원복 INSERT SQL을 먼저 준비합니다.

이 부분에서 확인할 것: 성공 기준: DB 담당자 승인 전에는 애플리케이션 writer를 켜지 않음.
  1. target Scheduler와 모든 application writer를 중지하되 미러 MariaDB는 격리 상태로 유지한다.
  2. A그룹 target 현 데이터를 data-only rollback SQL로 추출하고 B1 SQL을 staging DB에 선적재해 검증한다.
  3. A그룹 table의 데이터만 DELETE FROM으로 비운 뒤 검증된 B1 INSERT SQL을 적재한다. DB/schema/table을 drop·truncate하지 않는다.
  4. B그룹은 source/target 후보 PK 합집합의 target before-image를 저장한 뒤 tbl_manage_deploy, tbl_learn_recommend, tbl_deploy 후보행만 source 최종값으로 교체한다.
  5. tbl_bot은 영향 bot의 active/standby deploy·learn 컬럼만 source staging 값으로 UPDATE한다.
  6. A/B 이외 table 불변, A그룹 count/checksum/AUTO_INCREMENT, B그룹 후보행과 논리 orphan을 확인한다. MyISAM 적용 실패 시 target before-image로 역순 원복한다.

14.4 Redis·Solr·Elasticsearch R1

🧒 아주 쉽게 설명하면: 14.4 Redis·Solr·Elasticsearch R1

세 검색·cache 계층의 최종 상태를 target에서 맞추는 단계입니다.

Redis는 재결합 또는 cache 재생성, Solr는 모든 collection restore, Elasticsearch는 B1 snapshot restore와 정책 검증을 수행합니다.

서비스가 켜져 있는지만 보지 말고 cluster 상태·문서 수·대표 검색·alias·TTL·shard를 확인합니다.

조금 더 자세히: 실제 작업의 흐름

들어오는 자료: Redis 노드의 주소·port·master/replica 역할·node ID·slot 상태와 AOF/RDB 파일 정보입니다. Redis가 cache만 저장하는지, 로그인 세션·queue·업무 상태도 저장하는지는 애플리케이션 설정으로 확인합니다.

실제 흐름: PONG은 한 노드가 대답했다는 뜻이고, cluster_state:ok와 모든 slot 정상은 집단 전체가 일할 준비가 됐다는 뜻입니다. 기존 cluster 재결합이 안전하면 유지하고, 주소·node ID·slot이 꼬이면 빈 3 master/3 replica를 구성한 뒤 cache를 다시 만듭니다.

  1. 노드와 역할을 기록합니다.
  2. source와 target이 동시에 같은 cluster가 되지 않게 합니다.
  3. 재결합 또는 새 cluster 중 하나를 선택합니다.
  4. cache 재생성 뒤 TTL·대표 기능을 확인합니다.

주의: ‘Redis니까 지워도 된다’가 아닙니다. cache라면 다시 만들 수 있지만 세션·queue라면 초기화가 곧 업무 영향일 수 있으므로 담당자 승인이 필요합니다.

이 부분에서 확인할 것: NO-GO: 원본 endpoint 접근, collection/index 누락, Redis slot 미완료.
  1. DB 선택 재적재 보고서가 승인된 뒤 target cluster writer와 관련 application을 계속 정지한다.
  2. Redis/Solr/ZK/ES 리허설 상태는 ${HOLD_ROOT}/rehearsal-<RUN_ID>로 안전 보관한다.
  3. Redis는 B1 데이터를 import하지 않는다. cluster 합격값을 다시 확인하고, 리허설 cache가 남아 있으면 시스템 배포 기능의 full replace 여부에 따라 target cache를 승인된 방식으로 비운 뒤 전체 재배포한다.
  4. ZooKeeper/Solr를 빈 ensemble/cloud로 다시 만들고 B1 configset과 모든 collection을 restore한다. 하나라도 누락되면 중단한다.
  5. Elasticsearch의 미러·리허설 data를 working 경로에서 제외하고 빈 신규 cluster를 만든다. repository를 다시 등록하고 B1 application/Kibana index를 include_global_state:false로 restore한 뒤 정책 객체를 명시적으로 적용한다.
  6. 파일성 데이터는 B1 manifest와 DB 참조를 기준으로 승인된 최종 세트를 배치한다.
  7. B1 manifest와 target을 비교한 뒤 application을 기동한다. Scheduler는 여전히 OFF다.

14.5 최종 데이터 검증

🧒 아주 쉽게 설명하면: 14.5 최종 데이터 검증

운영 전환 전에 마지막 비교표를 만드는 단계입니다.

데이터가 같고 기능도 같아야 합니다. DB 행 수만 같아도 검색 index가 빠졌을 수 있고, 화면이 떠도 일부 업무 API가 실패할 수 있습니다.

데이터 검증과 업무 시나리오 검증을 모두 통과한 뒤에야 L4/VIP/DNS를 바꿉니다.

이 부분에서 확인할 것: 최종 산출물: 비교 결과, 로그, checksum, 담당자 서명, GO/NO-GO 판단.
  • master DB와 모든 tenant DB에서 A그룹 source/target 일치, B그룹 후보 PK 일치, 비대상 table 불변, AUTO_INCREMENT, 논리 orphan 0, 미완료 batch/deploy 상태 확인.
  • tbl_batch_log와 9개 통계 table은 source B1로 재적재되었고 target 리허설 이력은 rollback SQL에만 보존됨.
  • tbl_manage_deploy, tbl_deploy, tbl_bot, tbl_learn_recommend은 후보 PK/상태 컬럼만 교정되었고 DB·Solr·Redis·Engine 상태와 함께 업무 승인됨.
  • Redis 16384 slot·3M/3R·대표 cache/TTL, Solr collection 이름·count·alias·ktnori, ES index count/mapping/alias·ILM explain·SLM 시험 결과.
  • 모든 application이 source IP에 연결하지 않고 target hostname/VIP 설정만 사용.
binlog는 후보 발견용일 뿐 ROW binlog/GTID가 사용 가능하면 B0_SAFE 이후 B그룹 후보 PK 누락 여부를 교차 확인할 수 있다. binlog 전체 replay나 DB 전체 동기화에는 사용하지 않으며, 최종 적용 범위는 승인된 A그룹과 B그룹 후보 manifest로 제한한다.

16. GO/NO-GO와 롤백

🧒 아주 쉽게 설명하면: 16. GO/NO-GO와 롤백

GO는 다음 단계로 가고, NO-GO는 멈추는 신호입니다.

이관에서는 ‘일단 해 보고 문제면 고치자’보다, 미리 정한 통과 기준이 중요합니다. 백업·격리·데이터·기능·전환 단계마다 통과 기준을 둡니다.

롤백은 target을 지우는 일이 아니라, target 트래픽을 차단하고 source로 돌아가는 절차입니다. target에서 이미 쓰기가 발생했다면 데이터가 두 방향으로 달라질 수 있으므로 먼저 write 상태를 판단합니다.
